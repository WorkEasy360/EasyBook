# AUTOMATION

PURPOSE
Tenant-safe, event/schedule-driven automation engine (Phase 11): trigger -> conditions -> actions -> execution history. The top layer — sits above `ai` (calls `ai.orchestration.assist` for draft actions) and every module below it; nothing may import `automation`. Lower modules never import it either (e.g. `sales`) — automation listens to their EXISTING `post_save` signals instead (`receivers.py`), mirroring `ai/rag/signals.py`'s relationship with `documents`.

OWNS
- `models/rule.py` — `AutomationRule` (`RuleStatus`: DRAFT/ACTIVE/PAUSED/ARCHIVED via `services/rules.py::_ALLOWED_TRANSITIONS`). Only ACTIVE rules ever execute. `version` increments on any structural edit; `cooldown_days` throttles scan-based triggers only (see below).
- `models/condition.py` / `conditions/operators.py` / `conditions/schemas.py` / `conditions/evaluator.py` — `AutomationCondition` rows validated against a strict per-trigger field allowlist (never arbitrary attribute access, never `eval()`), then evaluated against freshly-reloaded facts (`triggers/facts.py` — never the event payload alone).
- `models/action.py` / `actions/registry.py` / `actions/handlers.py` — `AutomationActionConfig` validated against each action's own JSON schema. `register()` refuses `safety_level >= 3` structurally — a Level 3 action (post invoice, record payment, reconcile, submit GST, transfer stock, send payment) can never be reachable from this registry. Default catalog, all Level 1: `send_notification` (`models/notification.py::AutomationNotification`, in-app only — no email/SMS transport exists in this codebase), `generate_report` (wraps `sales.selectors.get_overdue_invoices` / `inventory.selectors.get_low_stock_items` — never re-derives), `draft_payment_reminder` (wraps `ai.orchestration.assist.draft_payment_reminder` verbatim — draft text only, never sent), `call_webhook` (`actions/webhook_security.py` SSRF checks + `actions/webhook_sender.py` HMAC-signed stdlib HTTP POST, gated behind the privileged `automation.manage_webhooks` permission — Owner/Admin only).
- `triggers/registry.py` — trigger catalog (identifiers/labels/category). Live event/schedule wiring exists for: `invoice.posted` (event, via `receivers.py`), `invoice.overdue` and `stock.low` (scan-based schedule, via `services/scheduling.py` + `tasks.py::run_due_scans_task`), `schedule.daily/weekly/monthly` (pure schedule, via `models/schedule.py::AutomationSchedule` + `run_due_schedules_task`), `manual`. Other registered triggers (`invoice.paid`, `bill.*`, `payment.received`, `document.ocr_completed`) accept rule configuration but have no live dispatch yet — see DEFERRED.
- `models/event.py` — `AutomationEvent`, the transactional outbox row a domain `post_save` receiver creates in the SAME transaction as the state change it describes. `models/execution.py` / `models/step_execution.py` — `AutomationExecution` (snapshots `conditions`/`actions`/`rule_version` at creation so a later rule edit can't rewrite history; `UniqueConstraint(rule, trigger_event)` is the authoritative same-event-twice guard) and `AutomationStepExecution` (`idempotency_key` = sha256(execution_id:action_id:order), stable across retries; RETRYING vs terminal FAILED per `RETRYABLE_CATEGORIES`).
- `models/schedule.py` — `AutomationSchedule`/`AutomationScheduleOccurrence` (pure schedule triggers, SKIP_MISSED policy) and `AutomationScanOccurrence` (scan-based triggers; combined with `AutomationRule.cooldown_days` to avoid re-firing every scan while an entity remains matched).
- `services/execution.py` — the engine: `create_execution_for_event`/`create_manual_execution`, `run_execution` (idempotent — safe to call again after a crash or for a bounded automatic retry), `retry_execution` (human-initiated, resets terminal FAILED steps). `ACTION_PERMISSIONS` re-verifies the executing user's CURRENT membership/role at every step (run-as policy, phase section 23) — never trusts what was valid when the rule was created.
- `services/events.py` — `record_event` (the outbox write) + `causation_context` (propagates causation_id/correlation_id/depth for a future domain-mutating action; enforces `settings.AUTOMATION_MAX_DEPTH`).
- `tasks.py` — Celery: `dispatch_automation_events_task` (outbox dispatcher, `SELECT ... FOR UPDATE SKIP LOCKED`), `run_execution_task` (bounded exponential backoff + jitter, `max_retries=5`, only for `RETRYING` steps), `run_due_schedules_task`, `run_due_scans_task`. Every task explicitly opens `tenant_context()` per organization — never assumes request middleware ran.
- `api/` — `/api/v1/automation/rules/` (list/create), `/rules/{id}/` (retrieve/update), `/rules/{id}/activate|pause|archive|run/`, `/executions/` (list/retrieve), `/executions/{id}/retry/`, `/catalog/triggers/`, `/catalog/actions/`.
- `authz` — `automation.view/create/edit/enable/disable/run/view_history/retry` (Owner/Admin/Accountant/Staff; Viewer view-only) and the privileged `automation.manage_webhooks` (Owner/Admin only) — see `authz/roles.py`.

DEFERRED (not built — do not claim these work)
- Level 2 actions (draft invoice/bill creation) — no domain-mutating action ships in Phase 11's default catalog, so `causation_context`'s depth-propagation is real but unexercised outside its own unit test.
- Live dispatch for `invoice.paid`, `bill.posted`, `bill.overdue`, `payment.received`, `document.ocr_completed` — registered as valid `trigger_type`s (a rule can be created and activated against them) but nothing emits or scans for them yet; add a `receivers.py` entry or a `services/scheduling.py` scan function the same way `invoice.posted`/`invoice.overdue` were wired.
- `AutomationApproval` (phase section 74-75) — no action in the default catalog needs human approval yet (all Level 1); the architecture (explicit action safety levels, a registry that refuses Level 3) does not preclude adding it later.
- A real email/SMS notification transport, `AUTOMATION_WEBHOOK_SENDER_BACKEND=http` in production use (never verified against a real endpoint — only the deterministic `fake` backend is exercised in tests), a dedicated encrypted secret store for webhook secrets (currently plaintext-at-rest in Postgres, masked only in API responses).
- Celery Beat schedule entries for `dispatch_automation_events_task`/`run_due_schedules_task`/`run_due_scans_task` — periodic invocation is a deployment decision left to whichever phase introduces `django-celery-beat`/`CELERY_BEAT_SCHEDULE` (none exists in this repo), same posture as `sales.tasks.generate_recurring_invoices_task`.

DOES NOT OWN
Accounting logic, inventory logic, sales/purchases logic, tax calculation, banking reconciliation, AI financial truth — automation only ever reaches these through their own domain services/selectors, never directly.

INVARIANTS
- Every model here is `TenantScopedModel` with a matching RLS migration — `tests/test_rls.py` asserts this exhaustively and dynamically (walks every model in the app), so a new model without an RLS migration fails the test rather than shipping unprotected.
- No arbitrary code/SQL/expression evaluation anywhere — `conditions/schemas.py`, `actions/registry.py` are the only places a string becomes a comparison or a config value, both via fixed allowlists.
- Automation never bypasses domain services — every action handler calls an existing selector/service; none constructs a `JournalLine`, mutates stock, or writes to another module's tables directly.
- AI actions are advisory/text-only; automation remains the authoritative execution decision-maker — a handler never feeds LLM output back in as a condition value, account ID, or payment instruction.
- Outbound webhook calls are SSRF-checked at BOTH rule-save/activate time and execution time (`actions/webhook_security.py`) and require HTTPS + the `automation.manage_webhooks` permission specifically, independent of `automation.create`/`edit`.
- Run-as permissions are re-verified live at every step execution, never cached from rule-creation time (`services/execution.py::_execute_step`).
- No class-level tenant-scoped `.objects.all()` querysets in `api/views.py` — always built in `get_queryset()` (core/CLAUDE.md).

TESTS
`tests/test_rls.py` (RLS coverage, dynamic over every model), `tests/test_rules.py` (lifecycle/validation/tenant isolation), `tests/test_conditions.py` (evaluator + fact builders), `tests/test_events.py` (outbox emission, tenant isolation, loop-prevention depth guard), `tests/test_execution.py` (condition matching, idempotent replay, run-as permission re-check, retry semantics, AI draft wiring), `tests/test_tasks.py` (dispatch/schedule/scan tasks, including a real-thread `TransactionTestCase` race for both scan-occurrence claiming and same-event double-dispatch), `tests/test_webhook.py` (SSRF checks, RBAC, signed delivery, secret masking), `tests/test_api.py` (RBAC + API surface).
