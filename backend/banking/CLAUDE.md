# BANKING

PURPOSE
Bank and credit card accounts, statement import, matching and period reconciliation. Phase 6 complete: Bank Accounts, Credit Card Accounts, Statement Imports (CSV), Bank Transactions, Matching (exact / amount+date / invoice / bill / expense / transfer detection), the four statuses, Rules, Transfers, and the reconciliation sign-off, with the RLS/concurrency acceptance gate (`tests/test_rls.py`, `tests/test_concurrency.py`, `tests/test_workflow_e2e.py`).

**A STATEMENT LINE IS EVIDENCE, NOT AN ACCOUNTING EVENT.** Importing posts nothing — the bank telling us money moved does not say which account it belongs to, and guessing is what reconciliation exists to avoid. Matching posts nothing either: the matched document already posted its own journal, and a second one would double the revenue. Only TWO paths in this app reach `accounting.services`, both through `accounting_bridge.py`: `services/transfers.py` (money genuinely moved between two of our accounts) and `services/matching.py::categorize_transaction` (a line with no document behind it, so the statement IS the first record). That is the same rule as `purchases.GoodsReceipt` moving stock without posting: a module posts only where it is the first place the financial fact becomes known.

OWNS
- `models/bank_account.py` — `BankAccount`. Paired 1:1 with the `accounting.Account` carrying its ledger balance, never merged with it: reconciliation is exactly the comparison of the two, so collapsing them leaves nothing to compare. `OneToOneField`, not FK — two bank accounts sharing one GL account would make every reconciliation permanently unexplainable. `kind` selects the required GL account type (BANK→ASSET, CREDIT_CARD→LIABILITY); a card paired to an asset account overstates cash by the card balance twice over. `account`/`kind` are absent from `update_bank_account` on purpose — both are "make a new bank account" operations. `opening_balance` is the STATEMENT balance at go-live and is deliberately NOT the GL opening balance (`accounting.services.opening_balances`' job): the two differ whenever the account was mid-reconciliation at go-live, and conflating them makes a first reconciliation impossible to close. It locks once statement lines exist.
- `models/statement.py` — `StatementImport`, `BankTransaction`. Bank-reported fields are frozen at insert (`_BANK_REPORTED_FIELDS`); what is mutable is our *interpretation* (status, exclusion, which reconciliation cleared it). `delete()` raises — deleting evidence is never the correction; exclusion is.
- `models/match.py` — `BankTransactionMatch`. Explicit FKs per counterpart rather than the `(source_type, source_id)` string pair `accounting.JournalEntry` uses, because here the database must actually protect the link: PROTECT stops a matched payment being deleted under a closed reconciliation. A `CheckConstraint` enforces exactly one counterpart.
- `models/transfer.py` — `BankTransfer`. No draft phase (a transfer is a fact when recorded, like `sales.CustomerPayment`), but voidable, because it is the one movement commonly recorded against the wrong pair of accounts. Financial fields frozen; correction is a reversing journal.
- `models/rule.py` — `BankRule`. `models/reconciliation.py` — `BankReconciliation`.
- `providers/` — the bank-feed seam. `selectors.py` — the three balances. `accounting_bridge.py` — the only entry into `accounting.services`.

**THE SIGN CONVENTION — one rule the whole app rests on.**
`BankTransaction.amount` is signed from the account holder's view: positive money in, negative money out. It maps to the ledger as **positive debits the bank's GL account, negative credits it** — and that single rule is correct for both kinds with no special case. A deposit debits an ASSET upward; a card repayment (positive: money arrived) debits the LIABILITY downward; a card purchase credits it upward. `selectors.get_book_balance` therefore sums debit-minus-credit DIRECTLY rather than calling `accounting.selectors.get_account_activity`, which flips sign for credit-normal accounts — a card's book balance must come out negative to compare against a card statement. One signed column beats separate deposit/withdrawal columns, which can both be populated, after which no reader agrees what the row means.

**THREE BALANCES, AND WHY THEY ARE THREE** (`selectors.py`)
`book` (posted JournalLines) / `statement` (imported lines) / `cleared` (the explained part of the statement). Reconciliation is the exercise of accounting for the gaps, so collapsing any two into one stored number deletes the thing being reconciled. `cleared` ≠ `statement` means work left to do. `book` ≠ `cleared` means genuine timing differences — outstanding cheques, deposits in transit — which are normal and are REPORTED (`uncleared_book_amount`), never treated as errors.

**DUPLICATE IMPORTS: A MULTISET DIFFERENCE, NOT A UNIQUE CONSTRAINT** (`services/imports.py`)
The realistic duplicate is not a re-uploaded file (the `file_hash` catches that, and it is the easy case) — it is 1–31 March downloaded on the 31st, then 15 March–15 April a fortnight later. Different bytes, overlapping rows. The tempting fix, a unique constraint on (account, date, amount, description), is wrong in the direction that loses money: two 500.00 ATM withdrawals on one day are byte-identical and both real. So for each fingerprint the file is asked how many it contains and the database how many it holds, and only the excess is imported. Two genuine withdrawals import as two; the same two in an overlapping file import as none; a bank splitting them across exports imports one then one. `external_id` (OFX FITID) replaces the derived fingerprint when present, since an institution-issued id survives a bank retidying its narration. The one case arithmetic cannot decide — an identical charge genuinely repeating in a later statement — is not guessed: `services/transactions.py::add_manual_transaction` lets a person add it, with an author and an audit record.

**EXCLUDE MEANS "NOT A REAL TRANSACTION", AND NOTHING ELSE**
It is the most abusable control in reconciliation software, because it is the fastest way to make a stubborn difference disappear. The definition is enforced by the arithmetic, not by documentation: `get_statement_balance` omits excluded lines entirely. That is correct ONLY for artefacts (a duplicate the bank emitted, a header row the parser read as data, a line belonging to another entity) — the bank's own closing balance excludes them too. A line that IS real but has no counterpart must be CATEGORIZED, which posts the journal the books were missing. Excluding it instead would hide a genuine difference and leave the ledger permanently short. A matched line cannot be excluded at all: if it matches a document, it demonstrably is real.

**SUGGESTION IS NOT CONFIRMATION, AND AMBIGUITY IS NEVER RESOLVED FOR THE USER** (`services/matching.py`)
`suggest_matches` writes unconfirmed rows and stops. `auto_match` confirms only when exactly ONE candidate clears `AUTO_CONFIRM_THRESHOLD`. Two customers each paying 25,000 on one day is the normal case, not an edge case, and breaking that tie by id order attributes a payment to the wrong customer and sends the wrong dunning letter. The threshold is 0.8 — what "exact amount, same day" scores — because the threshold is NOT what makes auto-confirmation safe; **uniqueness is**. No score can separate the right payment from an identical wrong one. What the threshold rules out is weak evidence. Setting it at 0.9 would demand the document's reference appear in the narration, which real bank narrations rarely carry, giving auto-matching that never fires — which in practice means every line gets clicked through unread.

**AI** — `SuggestionSource.AI` is load-bearing, not descriptive. `record_ai_suggestion` is the only way an AI-proposed match enters; it is refused auto-confirmation unconditionally and `confirm_match` demands a named human actor. No AI produces suggestions yet (Phase 10); the guard exists first, deliberately, because a control added after the feature it controls is a control that shipped late. Root CLAUDE.md: AI may suggest, deterministic logic performs the authoritative act — and reconciliation status IS an authoritative accounting fact.

**COMPLETION IS THE CONTROL, SO IT HAS NO OVERRIDE** (`services/reconciliation.py`)
Closing requires the cleared balance to equal the typed closing balance to the cent AND no line in the period still unmatched or suggested. There is no force-close flag, and its absence is the feature: a reconciliation closable over an unexplained difference certifies nothing, and carries an assurance it has not earned. The escape hatches are categorize and exclude, both of which leave a record with an author. `statement_closing_balance` is typed by a human from an outside document on purpose — derived from the imported lines it would agree by construction and prove nothing. Lines in a COMPLETED period are locked; correcting one requires `reopen_reconciliation`, which demands a reason and is audited.

RULES (`services/rules.py`)
First match wins, by priority; rules do not compose. A rule set where several rules each contribute is one where nobody can predict what a line will do and adding a rule silently changes lines the author never saw. Conditions are fixed columns with case-insensitive substring matching — deliberately not regex (a catastrophically backtracking user-supplied pattern hangs the import worker) and not an expression language (a sandbox problem). `auto_confirm` defaults FALSE, and that default is the point: an auto-confirming rule posts a journal unattended, which must be something the user switched on for a rule they trust, not something they find later in their P&L. A rule with no conditions is refused — it would categorize an entire statement to one account.

TRANSFERS
A transfer is net-zero for the business, and booking one as income is the most common way a self-serve ledger overstates revenue — which is why detection is first-class here rather than left to rules. `confirm_detected_transfer` posts exactly ONE journal for the pair: two lines are two views of one movement, and booking each separately doubles it and leaves both accounts wrong in opposite directions, which nets to zero on the trial balance and is invisible until someone reads the cash flow statement. Detection uses a 5-day window, deliberately narrower than `MATCH_WINDOW_DAYS`, because a wide window across several accounts turns every round-number payment into a transfer candidate. A transfer is the one counterpart whose capacity is one full amount **per leg** — it legitimately appears on two statements — which is why `get_counterpart_matched_amount` takes a `bank_account`. Cross-currency transfers are refused: the gap between legs is an FX gain or loss needing an account this phase has no convention for.

INVARIANTS
- Decimal only for money, everywhere.
- Accounting effects only via `accounting_bridge.py::post_banking_journal`, and only from `transfers.py` and `categorize_transaction`. Import and match post nothing.
- Every derived-total check (`get_matched_amount`, `get_counterpart_matched_amount`, the import's occurrence count) is taken UNDER A LOCK. The statement line alone is not enough: five deposits confirmed at once each lock a different line, so nothing serialises them and one payment ends up explaining all five. `_lock_counterpart` locks the document. Covered by `tests/test_concurrency.py`.
- Only the last four digits of an account or card number are ever stored (root CLAUDE.md: never store raw card credentials). Truncation happens in `services/bank_accounts.py::_last4` rather than validation-and-storage, so a pasted full number cannot persist — including into an error message. Not in `__str__`, not in `list_display`, and redacted in the audit trail.
- Tenant isolation mandatory — every model is `TenantScopedModel` with a matching RLS migration; `tests/test_rls.py` fails if a new model appears without one. This app holds the most sensitive data in the product: a statement discloses every counterparty and every amount.
- No class-level tenant-scoped `.objects.all()` querysets — always build in `get_queryset()`.

RBAC NOTE
Statement VISIBILITY follows the existing `VIEW_ACCOUNTING` grant rather than a stricter new tier: Staff already read the General Ledger, which contains every bank journal, so hiding the statement would be theatre. What stops at Accountant is the authority to decide what the books SAY — `IMPORT_BANK_STATEMENT`, `RECONCILE_BANK` (which certifies a balance), `MANAGE_BANK_RULES` (an auto-confirming rule posts unattended) and `RECORD_BANK_TRANSFER`, which moves money and therefore sits beside `RECORD_VENDOR_PAYMENT` on the same segregation-of-duties line. Asserted by `authz/tests/test_roles.py`.

DELIBERATELY NOT BUILT
- **No live bank feed.** `providers/base.py` is the seam; `ManualImportProvider` is the only implementation. No Plaid / Salt Edge / Yodlee / account-aggregator provider exists because root CLAUDE.md forbids inventing APIs and requires verification against official documentation — a provider written from memory looks finished, passes tests written from the same memory, and fails on first contact. All of them also need credentials and a commercial agreement that do not exist. Adding one is a new class plus a settings entry, returning the same `ParsedTransaction` records, so dedupe/rules/matching are unchanged.
- **No OFX/QIF parser.** The brief allows them "where justified". A correct OFX reader is an SGML-ish parser with a 1.x/2.x version split, institution-specific quirks and its own entity-expansion attack surface — it needs a maintained library and real bank samples to test against. A hand-rolled one works on the sample its author imagined, which on financial data is worse than not offering the format. `StatementFormat` already carries both.
- **No inferred column mapping in the import path.** `suggest_column_mapping` exists for a UI to pre-fill, and nothing in the importer calls it. Guessing which column is the amount, or whether a withdrawal column is already negative, books every withdrawal as a deposit.

TEST GOTCHA
`BankingTestsBase` / `BankingTransactionTestsBase` split off `BankingFixtureMixin` for the same reason `purchases.tests.base` does — `TestCase` subclasses `TransactionTestCase`, so mixing them directly silently yields `TestCase` semantics, and the concurrency races need committed rows visible to a second connection.

Note also: two audit entries written in the same clock tick can share `created_at` to the microsecond (Windows' ~15ms timer resolution), so `AuditLog.objects.order_by("-created_at").first()` is not a reliable way to select "the entry for the thing I just did". Select by `action` instead.
