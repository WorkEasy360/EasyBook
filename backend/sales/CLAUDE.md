# SALES

PURPOSE
Owns customer sales lifecycle from quote through payment and credit. Phase 3 complete: Customers, Quotes, Sales Orders, Delivery Challans, Invoices, Payments, Credit Notes, Recurring Invoices, RBAC/audit hardening, and the RLS/concurrency/idempotency acceptance gate (`tests/test_concurrency.py`).

OWNS
- `models/customer.py` — `Customer`, org-scoped sales-side customer master data. Deliberately not a shared CRM Contact/Company entity (none exists elsewhere in the codebase).
- `models/quote.py` — `Quote`/`QuoteLine`. Non-binding, creates NO accounting entries and NO inventory movements. Numbered at creation (unlike JournalEntry/Invoice, which number at posting) since it's never an authoritative financial record.
- `models/sales_order.py` — `SalesOrder`/`SalesOrderLine`. Also creates NO accounting entries. `source_quote` is a `OneToOneField` (a quote converts to at most one order, mirrors `JournalEntry.reverses`). `PARTIALLY_FULFILLED`/`FULFILLED` are derived by `services/sales_orders.py::refresh_order_fulfillment_status` from `DeliveryChallanLine` rows — never a stored quantity on the line. Deliberately no stock-reservation logic (root CLAUDE.md: don't invent it unless required).
- `models/delivery.py` — `DeliveryChallan`/`DeliveryChallanLine`. Creates a quantity-only `StockMovement` (ISSUE) at dispatch — deliberately NEVER an accounting journal; COGS/Inventory Asset posts at Invoice time instead (matching principle: COGS recognized alongside revenue, not at physical dispatch — see INVOICE INVENTORY in the phase spec). Lines carry no pricing/tax — a challan has no revenue impact. `source_order_line` (nullable FK to `SalesOrderLine`) is the only record fulfillment is derived from.
- `models/invoice.py` — `Invoice`/`InvoiceLine`. The first genuinely authoritative financial record in `sales` — numbered at POST time (not creation), like `JournalEntry`. `source_quote` is a `OneToOneField` (same convert-once pattern as `SalesOrder`). No `amount_paid`/`amount_due` columns — see `selectors.py`. `receivable_account`/`tax_payable_account` are explicit, caller-supplied fields (no `is_ar`/`is_tax_payable` flag exists on `accounting.Account` to auto-detect them from — same "no implicit account invented" principle as `inventory.StockAdjustment.contra_account`).
- `services/customers.py` — `create_customer`/`update_customer`/`archive_customer`, plus `assert_customer_usable_for_new_transaction` (the shared guard every sales service must call before attaching a customer to a new document).
- `services/quotes.py` — `create_quote`/`replace_quote_lines` (DRAFT only) and the explicit state-transition functions `send_quote`/`accept_quote`/`reject_quote`/`cancel_quote`. `_ALLOWED_TRANSITIONS` is the single source of truth for legal status edges.
- `services/sales_orders.py` — `create_sales_order`/`replace_order_lines` (DRAFT only), `confirm_order`/`cancel_order`, `convert_quote_to_sales_order` (only from an `ACCEPTED` quote; raises if the quote already has a `sales_order`), and `refresh_order_fulfillment_status` (called only by `services/deliveries.py`, never by a user-facing endpoint).
- `services/deliveries.py` — `create_delivery_challan`/`replace_delivery_lines` (DRAFT only), `dispatch_delivery` (idempotent like `accounting.services.posting.post_journal` — dispatching an already-DISPATCHED challan is a locked no-op, never double-issuing stock), `mark_delivered`, `cancel_delivery` (DRAFT only — once dispatched, stock has moved and cancellation is out of scope for this slice). OUT movements are valued at the weighted-average cost computed at dispatch time via `inventory.selectors.get_weighted_average_cost`, same pattern as `inventory.services.adjustments.post_stock_adjustment`.
- `services/invoices.py` — `create_invoice`/`replace_invoice_lines` (DRAFT only), `convert_quote_to_invoice` (only from `ACCEPTED`, raises if already converted), `post_invoice` (idempotent — DRAFT -> SENT, allocates `invoice_number`, posts ONE journal covering AR/Revenue/Tax and, where applicable, COGS/Inventory Asset, issues stock ONLY for lines with no linked `source_delivery_challan_line`), `void_invoice` (idempotent — reverses the journal via `accounting.services.posting.reverse_journal` and reverses only DIRECTLY-issued stock; refuses if any payment is allocated), and `refresh_invoice_payment_status` (called only by `services/payments.py`, never by a user-facing endpoint). See INVOICE INVENTORY logic below.
- `models/payment.py` — `CustomerPayment`/`PaymentAllocation`. Unlike every other sales document, a payment has no DRAFT phase — it's a completed fact from creation, so both models are append-only from the first save (same pattern as `inventory.StockMovement`/`audit.AuditLog`), not merely "immutable after leaving draft". `PaymentAllocation.invoice` is nullable: a null-invoice row is unapplied customer credit (root CLAUDE.md §27 — overpayment becomes credit, never a negative invoice balance, never silently over-allocated).
- `services/payments.py` — `record_payment`, the only way to create a `CustomerPayment`. Locks (`select_for_update`) every invoice it allocates against before checking `get_invoice_amount_due`, so two concurrent payments against the same invoice can't both succeed in over-allocating it (same pattern as `inventory.services.movements.record_stock_movement`'s negative-stock guard). Builds the `CustomerPayment` row's id up front (`uuid.uuid4()`) so the accounting journal can be posted — and `accounting_journal` set — in the SAME `.create()` call; a payment's `save()` guard forbids a second `.save()` to patch it in afterward. Has no DRAFT/POSTED status to make posting idempotent-by-construction (unlike `post_invoice`), so duplicate-request safety is the caller's job via the `Idempotency-Key` header (`core.idempotency`) — see `api/views.py::CustomerPaymentListCreateView`.
- `accounting_bridge.py` — `post_sales_journal`, the ONLY sales-layer entry point into `accounting.services` (mirrors `inventory/services/accounting_bridge.py`). Purely mechanical: callers (`services/invoices.py`, `services/payments.py`) build pre-grouped, pre-balanced `{"account_id", "debit"/"credit"}` line dicts; this module just wraps `create_draft_journal` + `post_journal`.
- `services/line_items.py` — `validate_item_for_line`/`build_line_snapshot`, the shared item-validation + item-time-snapshot builder used by every PRICED document line type (Quote, SalesOrder, Invoice) — NOT used by `DeliveryChallanLine`, which has no price/tax to snapshot.
- **Moved in Phase 4**: `services/calculations.py` is now `core/money.py`, and `PaymentMethod`/`RecurringFrequency` now live in `core/enums.py` (re-exported from `models/payment.py` and `models/recurring_invoice.py`, so import paths here are unchanged). `_advance` is now `core.recurrence.advance_occurrence`. All four moved when `purchases` needed the same logic — see `core/CLAUDE.md`. Money still rounds to 2dp via `ROUND_HALF_UP` at the line level; document totals sum already-rounded line amounts rather than re-rounding.
- `selectors.py` — `get_fulfilled_quantity` (DeliveryChallanLine sum); `get_invoice_amount_paid`/`get_invoice_amount_due` (real `PaymentAllocation` sums now); `get_payment_unapplied_amount`; `get_outstanding_invoices`/`get_overdue_invoices` (live queries, not a stored "overdue" status — see `InvoiceStatus.OVERDUE`). All cross-document sums, never cached fields — same principle as inventory stock-on-hand/GL.
- **INVOICE INVENTORY logic** (`services/invoices.py::post_invoice`, `void_invoice`): a PRODUCT/`track_inventory` line either (a) has `source_delivery_challan_line` set — stock was already issued by that challan; posting does NOT issue again, but DOES recognize COGS using the average cost replayed `as_of` the challan's dispatch date (outbound movements never change `average_cost`, so this recovers the exact historical cost basis without needing a per-line stored cost) — or (b) has none — posting issues stock itself via `record_stock_movement`, using `Invoice.warehouse` (required in this case) and today's weighted-average cost. COGS/Inventory Asset lines are skipped (quantity-only) when the item lacks `inventory_account`/`cogs_account`, mirroring inventory's own "financially neutral" precedent. Voiding reverses only stock the invoice itself issued (`MovementType.ADJUSTMENT_IN`) — never stock genuinely shipped via a Delivery Challan, which remains a separate physical fact.
- **Fixed in Slice 6**: `core.models.IdempotencyKey.response_body` was a plain `JSONField()` with no `encoder=DjangoJSONEncoder` — the first real caller of `core.idempotency` (`CustomerPaymentListCreateView`) hit `TypeError: Object of type UUID is not JSON serializable` storing a real DRF `Response.data`. Fixed at the field definition (`core/models.py`), not worked around per call site — every future user of the idempotency foundation benefits.
- `models/credit_note.py` — `CreditNote`/`CreditNoteLine`. Numbered at ISSUE time, like Invoice. `source_invoice` is a plain FK, NOT `OneToOneField` — unlike Quote->SalesOrder/Invoice, one invoice may receive several partial credit notes over time. `source_invoice=None` means a standalone customer credit (e.g. goodwill), not tied to any invoice. `CreditNoteLine.restock` (default `False`) is the ONLY trigger for a stock movement — root CLAUDE.md: never restock automatically; `services/credit_notes.py` rejects `restock=True` outright for a SERVICE item rather than silently ignoring it. `amount_applied_to_invoice` is set ONCE at issue time and is a frozen historical fact (see selectors.py), unlike Invoice's amount_paid/amount_due which stay fully live — the difference is that a credit note's AR-vs-unapplied-credit split is a decision made at that moment (`get_invoice_amount_due` as it stood then), not a value safely re-derivable later.
- `services/credit_notes.py` — `create_credit_note`/`replace_credit_note_lines` (DRAFT only), `issue_credit_note` (idempotent — DRAFT -> ISSUED; nets the credit against `source_invoice`'s remaining balance up to `get_invoice_amount_due`, any excess — or the whole amount for a standalone credit — going to `unapplied_credit_account`, same §27 pattern `services/payments.py` uses for overpayment; posts Dr Revenue reversal + Dr Tax reversal against Cr AR/Cr unapplied-credit, plus Dr Inventory Asset/Cr COGS for any `restock=True` lines; calls `services/invoices.py::refresh_invoice_payment_status` afterward since crediting can also settle an invoice), and `void_credit_note` (idempotent — reverses the journal and any restock via `MovementType.ADJUSTMENT_OUT`, the exact counter-pairing of the restock's own `ADJUSTMENT_IN`, mirroring `inventory.services.adjustments.reverse_stock_adjustment`'s IN/OUT flip convention). The original invoice is never mutated — see INVOICE INVENTORY logic and root CLAUDE.md.
- `models/recurring_invoice.py` — `RecurringInvoiceTemplate`/`RecurringInvoiceTemplateLine`/`RecurringInvoiceRun`. No DRAFT lifecycle (a template is just a live, directly-editable schedule, like `Customer` — not gated like Quote/Order/Invoice/CreditNote). `RecurringInvoiceRun` is the append-only idempotency ledger: a `UniqueConstraint` on `(template, occurrence_date)` is the AUTHORITATIVE guard against generating the same occurrence twice, with `select_for_update()` on the template as the (redundant-by-design) fast path — same belt-and-braces pattern as `items.Item`'s DB `CheckConstraint` backing up its service-layer validation.
- `services/recurring_invoices.py` — `create_recurring_template`/`update_recurring_template`/`activate_template`/`deactivate_template`, and `generate_due_invoices` (the Celery entry point, called only from `tasks.py`, never inline in a web request — root CLAUDE.md). Generates DRAFT invoices ONLY — never posts accounting/stock; a human reviews and calls `post_invoice`. Catches up multiple missed occurrences in one call (advances `next_run_at` one period at a time until caught up to `as_of`/`end_date`). **Not tenant-scoped itself** — a scheduled task spans every organization — so it enumerates `accounts.Organization` first (deliberately NOT RLS-protected — see accounts/CLAUDE.md) and opens `tenant_context()` per organization. This is NOT optional: RLS is enforced at the Postgres level independent of which Django manager is used (`all_objects` does NOT bypass it — core/CLAUDE.md's "TenantManager fails closed... RLS enforces the same boundary independent of application code correctness" applies just as much to a plain `models.Manager()` as to `TenantManager`); querying any RLS-protected table with no GUC set returns zero rows regardless of manager. `tasks.py` (Celery task `generate_recurring_invoices_task`) is a thin wrapper; scheduled hourly via the plain `CELERY_BEAT_SCHEDULE` entry `sales-generate-recurring-invoices` in `config/settings/base.py` (phase 12 slice 6) — no `django-celery-beat` dependency needed since interval-based scheduling doesn't require one.
- **Test gotcha** (see `tests/test_recurring_invoices.py`): any test calling `generate_due_invoices()` needs `TransactionTestCase`, not `TestCase`. Under `TestCase`'s outer wrapping transaction, each `tenant_context()` call inside the function becomes a SAVEPOINT rather than a true top-level transaction — and Postgres only reverts a `SET LOCAL` GUC on ROLLBACK, never on a savepoint RELEASE. Since the function loops over every organization (including ones irrelevant to the test), the last org processed leaks its GUC into whatever runs next in the test, breaking assertions scoped to a different org. `TransactionTestCase` gives real transaction boundaries, matching production Celery execution.
- `api/` — Customers under `/api/v1/sales/customers/`; Quotes under `/api/v1/sales/quotes/` plus `/send/`, `/accept/`, `/reject/`, `/cancel/`, `/convert/` (`target`: `"sales_order"` or `"invoice"`); Sales Orders under `/api/v1/sales/orders/` plus `/confirm/`, `/cancel/`; Delivery Challans under `/api/v1/sales/deliveries/` plus `/dispatch/`, `/deliver/`, `/cancel/`; Invoices under `/api/v1/sales/invoices/` plus `/post/`, `/void/`; Payments under `/api/v1/sales/payments/` (list/create + retrieve only — no update/void, append-only), create honors an `Idempotency-Key` header; Credit Notes under `/api/v1/sales/credit-notes/` plus `/issue/`, `/void/`; Recurring Invoice Templates under `/api/v1/sales/recurring-invoices/` plus `/activate/`, `/deactivate/` (no manual "generate now" endpoint — generation is Celery-only).
- **Fixed in Slice 9** (API/RBAC/audit hardening pass): `CreditNoteDetailView` hardcoded `required_permission = Permission.ISSUE_CREDIT_NOTE` for every HTTP method instead of the GET/write `@property` split every sibling detail view uses — silently blocked Viewers (who hold `VIEW_CREDIT_NOTES`) from retrieving a single credit note despite being able to list them. Fixed to match the established pattern; regression tests added (`test_viewer_can_retrieve_credit_note_detail`, `test_viewer_cannot_patch_credit_note`).
- `tests/test_concurrency.py` (Slice 10 acceptance gate) — `TransactionTestCase`-based races proving: concurrent `post_invoice` on the same invoice posts exactly one journal (idempotent-by-construction, no errors); concurrent `record_payment` against the same invoice can't jointly overpay it (exactly one succeeds, the rest rejected — as `over_allocation` or `invoice_not_payable` depending on lock-acquisition order, never silently double-allocated); concurrent `post_invoice` calls racing the same limited (item, warehouse) stock can't oversell it (exactly one succeeds, the loser gets `insufficient_stock`, final on-hand never negative); and a forced mid-`post_invoice` failure (after stock issue, before journal posting) rolls back the whole atomic block — no orphan `StockMovement`, no orphan `JournalEntry`, invoice stays DRAFT with no `invoice_number` allocated. NumberSequence concurrency is NOT duplicated here — `accounts/tests/test_number_sequence.py` already proves `allocate_sequence_number` (shared by every sales document's numbering) is race-safe.

INVARIANTS
- Every document is refused unless it is in the organization's base currency at rate 1 (`accounting.services.currency.assert_base_currency`) — multi-currency accounting does not exist yet.
- Decimal only for money fields, everywhere.
- Server-side totals are authoritative — `calculate_line`/`calculate_document_totals` are the only place rounding happens; never trust client-submitted totals (see API tests asserting a client-supplied `total` is ignored).
- Tenant-scoped model references in plain (non-`ModelSerializer`) API input — `customer_id`, `item_id` — are accepted as bare UUID fields and resolved to instances at request time via `Model.objects.get/filter(...)` inside `create()`/`save()`, never as a `PrimaryKeyRelatedField(queryset=TenantScopedModel.objects.all())` class attribute (that queryset would evaluate once at import time, before tenant context exists, permanently baking in `.none()` — same class-level-queryset trap as core/CLAUDE.md's view warning, mirrors `inventory/api/serializers.py`). `ModelSerializer`-auto-generated FK fields (e.g. `Quote.customer` on `QuoteSerializer`) are safe as-is — DRF builds those lazily per-request.
- Posted invoices immutable — enforced at the model layer (`Invoice.save()`/`InvoiceLine.save()` guards), mirroring `accounting.JournalEntry` exactly.
- Quotes/Sales Orders/Delivery Challans/Invoices/Credit Notes that have left DRAFT are immutable except through their own services — same model-layer guard pattern throughout.
- Accounting effects only via `accounting.services.journals`/`posting`, reached only through `sales/accounting_bridge.py::post_sales_journal` — never construct a `JournalLine` directly from this app. Delivery Challans deliberately post NO journal at all (see `models/delivery.py`); Invoices and Credit Notes each post exactly one journal per post-or-issue/void.
- Stock effects only via `inventory.services.movements.record_stock_movement` — never mutate stock directly. `select_for_update()` queries in this app never `.select_related()` a nullable FK (e.g. `DeliveryChallanLine.source_order_line`) — PostgreSQL rejects `FOR UPDATE` across a LEFT JOIN ("cannot be applied to the nullable side of an outer join"); only non-nullable FKs (`item`) are safe to join in a locked query.
- No mutable customer balance — receivable/outstanding is always derived from Invoice/Payment/CreditNote data, never stored on `Customer`. Applies to `Invoice.amount_paid`/`amount_due` too — see `selectors.py`. The one deliberate exception is `CreditNote.amount_applied_to_invoice`, frozen at issue time (see `models/credit_note.py`) — not a live balance, a historical fact.
- Historical document lines use snapshots, not live FK lookups — `QuoteLine`/`SalesOrderLine`/`InvoiceLine`/`CreditNoteLine` copy `description`/`hsn_sac_snapshot`/`tax_label` from the `Item` at creation time only (via `services/line_items.py`). `DeliveryChallanLine` has no snapshot fields — it isn't a priced document. A credit note never mutates the invoice it references — `Invoice.total`/lines are read-only from `services/credit_notes.py`.
- State transitions go through explicit services, never arbitrary status field edits — see `_ALLOWED_TRANSITIONS` in `services/quotes.py` and `services/sales_orders.py`, and the explicit status checks in `services/deliveries.py`, `services/invoices.py`, and `services/credit_notes.py`.
- Idempotency required for financial transitions — `dispatch_delivery`/`post_invoice`/`void_invoice`/`issue_credit_note`/`void_credit_note` are all idempotent-by-construction (locked no-op on repeat, exactly like `accounting.services.posting.post_journal`); `record_payment` has no status to exploit for that, so it relies on the `Idempotency-Key` header instead (`core.idempotency.IdempotencyKey`) — two different mechanisms for the same guarantee, chosen per whether the resource has a natural DRAFT/POSTED lifecycle.
- Tenant isolation mandatory — every model here is `TenantScopedModel` with a matching RLS migration.
- No class-level tenant-scoped `.objects.all()` querysets — always build in `get_queryset()` (see `core/CLAUDE.md`).
- `customer_code` is unique per organization; inactive customers/items are rejected for NEW transactions, but existing historical transactions referencing an archived customer/item remain fully accessible (`on_delete=PROTECT` everywhere a later model FKs to `Customer`/`Item`).
